# ComfyUI model integrity verification

## Baseline and diagnosis

Browser readiness currently resolves models by loader filenames (`frontend/src/browser/requirements.ts:107-117`), and the global queue guard cannot detect a truncated file after an interrupted download. Filed diagnosis: confirmed that the live isolated ComfyUI loader listed a final filename during download; a complete false-Ready outcome after interruption remains unproven. The model catalog supplies expected sizes and SHA-256 (`frontend/src/browser/catalog.ts:5-7`), while the existing Python verifier validates size, safetensors headers, and optionally SHA-256 (`src/marcostudio/comfy/model_paths.py:95-139`). The portable custom-node package registers a versioned capabilities endpoint (`src/marcostudio/comfy_nodes/__init__.py:32-50`) and is exported by `src/marcostudio/browser_export.py:104-119`.

## Proposed change and assumptions

Investigate extending the portable ComfyUI-side package with a narrowly scoped integrity capability backed by trusted catalog identities and expected digests. Resolve only approved model categories and names through ComfyUI's configured model paths; do not accept arbitrary filesystem paths or disclose paths or raw errors. Run bounded, deduplicated SHA-256 work off the server event loop, report queued/running/verified/failed states, detect file identity or metadata changes before and after hashing, and invalidate stale results. The browser must distinguish missing or incompatible helper, running verification, invalid result, and errors; never equate an unknown response with verified. Keep explicit consent and disclose hashing cost. Verify each API and schema against the installed ComfyUI source and vendor documentation before implementation.

## Security and limits

CORS is not authorization. Before adding a costly endpoint, reproduce how requests reach ComfyUI and decide what prevents an unrelated local or network caller from triggering repeated expensive hashes or enumerating files. Require explicit resource bounds and no caller-supplied expected hashes; if existing ComfyUI cannot supply an adequate trust boundary, stop short of exposing a new endpoint and report the blocker. A valid hash can become stale after verification, so verify file identity on reuse and describe the remaining interval before model load. Catalog changes and duplicate files must be handled without silently verifying the wrong model.

Proposed admission boundary: an opt-in helper generates a high-entropy pairing secret delivered only through an owner-controlled local channel; an authenticated header is required before any hash or model-existence disclosure. Never return it from an unauthenticated route, place it in a URL, or transmit it over an unprotected remote network. For non-loopback use, require an authenticated TLS proxy/tunnel or decline pairing. This protects only the helper, not other ComfyUI routes. Verify the actual user-accessible pairing path and origin/host behavior with hostile-origin, direct/no-Origin, invalid-token and legitimate-client controls before adding the endpoint. If that cannot be proven, stop and report rather than substituting CORS for authentication. Use one worker, a bounded queue of trusted IDs, deduplication, cancellation, and a bounded retry/cooldown policy; no poll-triggered rehash. Demonstrate ordinary health/queue responsiveness during a synthetic verification and measure actual resource costs, not a guessed ETA.

The concrete proposal is a randomly generated per-instance token, stored only in an owner-readable local file and revealed through an explicit owner-operated local CLI command, never a ComfyUI route or general server log. The user enters it in the browser; store it in session-scoped memory only, clear it on unpair/tab close, and rotate/revoke through the local owner channel. Reject non-loopback plain HTTP before sending the token. Require bearer authorization for start, status and cancel, and bind status IDs to the paired instance; verify preflight and supported browser behavior against the isolated server before shipping. Unsupported pairing or private-network access leaves readiness unverified with a clear manual path.

Do not put the token under ComfyUI's served user-data roots: installed `app/user_manager.py:334-363` serves user files through the server account. Prove the chosen location is outside all served roots, including configured overrides and symlinks. POSIX mode 0600 does not establish a Windows owner-only ACL; choose and test a Windows ACL or OS credential-store mechanism before claiming Windows support. The isolated server's local-origin preflight allowed Authorization, but a probe with the hosted origin did not establish browser private-network compatibility; prove hosted-browser access separately and do not treat a curl response as browser success.

Security control observed on the isolated test server: a synthetic token in a mode-0700 directory under its user-data root was returned over `/userdata/` with HTTP 200 despite restrictive file permissions. A prototype that checks only the immediate directory is unsafe and must not be integrated. Verify every served root, override and symlink boundary with HTTP controls, or use an actual owner-only credential store; fail closed if the boundary cannot be established.

Windows Credential Manager via the OS API is a candidate, not a verified integration: confirm the helper and owner CLI run as the same user and that read, revoke and rotate work on actual Desktop and portable Windows installs. The owner-only reveal may appear in terminal scrollback; do not claim otherwise. Python documents Windows `st_ctime` as creation time, so do not use the POSIX stat tuple as a sufficient Windows change token for cache reuse. Use a validated platform-specific change token or disable cache reuse and re-hash; detect cancellation immediately before success and bound file reads to the expected size plus a growth check.

Use at most one active hash and one pending model, with no caller-chosen digest; coalesce identical requests and reject extra work as busy. After completion, re-use a valid cached result and enforce a minimum five-minute cooldown for repeating the same failed identity unless explicitly reset by the owner. Cancellation is cooperative between chunks, never marks a file verified, and cannot start replacement work until the worker exits. Polling never starts work. Cache keys include catalog digest, category, exact loader-resolved path identity and file stat; check for active Manager work and re-stat before returning verified. Ambiguous paths, stale identities, inaccessible files or interrupted workers remain unverified. Test bounded work under bursts and verify health/queue response latency with measured isolated baseline and under load; treat a material regression as a blocker rather than inventing a universal time target.

Bundle a deterministic trusted catalog with both the browser node ZIP and CLI node installer (`src/marcostudio/browser_export.py:114-119`, `src/marcostudio/comfy/install.py:14-19`), and match a version/digest with the frontend; mismatches are unverified. Share only a dependency-light verifier core with the CLI, without importing torch-dependent node initialization in CLI tests. Register routes independently on repeated initialization. Resolve exactly the same configured-root/name that the loader will use; define and test duplicate roots, symlinks, path replacement, and any mismatch with the CLI's duplicate-name rules. Only a revalidated file identity can reuse cached results; restart and changed identity invalidate caches.

## Success and tests

Verify a valid fixture, truncated file, same-size corrupt file, missing file, path traversal, duplicate roots, symlinks, changed file during hash, repeated/concurrent requests, helper unavailable/version mismatch, browser refresh, active downloads, and manual-only installations. Test actual browser-to-helper behavior using an isolated ComfyUI test copy and small synthetic fixtures, never the production installation. Measure bounded worker concurrency and ensure long hashes do not block normal health or queue requests. Regenerate and compare the node ZIP, catalog and application bundle.

## Rollout and rollback

Develop and review in isolation; users install/update the helper and restart ComfyUI only when they choose. Explain the helper requirement and verification cost, then recheck. Roll back by reverting the feature commit and redeploying the earlier package; do not delete user models or nodes. The public PR and deployment are separate states.

Existing users with valid models receive an explicit unverified state and helper setup path; do not re-download or auto-install. Specify old-client/new-helper and new-client/old-helper behavior, and let users separately retain, update, or roll back the node installation. The browser Ready guarantee is the immediate scope; document the independent Python CLI verification behavior rather than claiming the two paths are identical.

Compatibility matrix: an old client with the new helper retains its prior filename-based behavior and must not be described as verified; a new client with an old, absent, or catalog-mismatched helper is unverified and offers the owner-controlled install/pairing path without redownloading models. Before implementing the endpoint, establish how the bundled local CLI is invoked on Desktop, portable and manual installations and prove the owner-only pairing flow and supported browser access; stop if this cannot be done safely. For rollback, the user retains the previous node bundle, explicitly replaces only the managed helper files with that known version and restarts ComfyUI when idle; reverting the frontend alone does not roll back an installed helper.

## Open questions, dependencies, trade-offs and non-goals

Verify that owner pairing actually provides the proposed authorization boundary in supported ComfyUI network/CORS configurations, that the helper can be packaged and rolled back safely, and that refusal leaves a clear unverified UI. Hashing can take significant time and disk I/O. Depend on ComfyUI folder resolution and portable-node distribution; no new external service, generation run, production ComfyUI mutation, or claim that a size/header check proves a checksum.
